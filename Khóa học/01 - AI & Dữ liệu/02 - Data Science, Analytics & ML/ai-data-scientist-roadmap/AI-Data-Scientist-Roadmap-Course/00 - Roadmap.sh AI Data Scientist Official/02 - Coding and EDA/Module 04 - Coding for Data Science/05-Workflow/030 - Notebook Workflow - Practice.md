## 1. Summary

This lesson explains **Notebook Workflow** in the context of AI engineering and data science.

A notebook is an interactive environment that combines:

* Executable code
* Markdown explanations
* Tables
* Charts
* Mathematical formulas
* Experiment results

Jupyter Notebook and JupyterLab are commonly used for:

* Exploratory data analysis
* Data cleaning
* Feature engineering
* Statistical analysis
* Model experiments
* Result visualization
* Technical communication

However, a notebook is useful only when it can be executed in a clear and reproducible order.

A good notebook should allow another person to answer:

* What problem is being investigated?
* What data is being used?
* How was the data cleaned?
* What assumptions were made?
* Which metrics were calculated?

## 3. What Is a Notebook Workflow?

A **notebook workflow** is the structured process used to move from a data question to a reproducible analysis inside a notebook.

A typical workflow is:

```text
Problem definition
        |
        v
Environment setup
        |
        v
Data loading
        |
        v
Data validation
        |
        v
Data cleaning
        |
        v
Exploratory data analysis
        |
        v
Feature engineering
        |
        v
Modeling or statistical analysis
        |
        v
Evaluation
        |
        v
Insights and recommendations
```

The notebook should tell a logical story rather than being a collection of unrelated code cells.

---

## 4. Why Notebook Workflow Matters

Data science work is highly iterative.

You may repeatedly:

* Change a filtering condition
* Add a new feature
* Replace a missing-value strategy
* Test another model
* Modify a chart
* Recalculate a metric

Without a clear workflow, the notebook may depend on:

* Cells executed in the wrong order
* Variables created many cells earlier
* Manual file edits
* Temporary local files
* Undocumented assumptions
* Outputs generated by outdated code

This creates a notebook that appears correct but cannot be reproduced.

A good workflow helps make the analysis:

* Reproducible
* Reviewable
* Debuggable
* Maintainable
* Shareable
* Easier to convert into production code

## 11. Step 5: Clean the Data

Cleaning steps should be explicit and reproducible.

### 11.1 Standardize Column Names

```python
sales.columns = (
    sales.columns
    .str.strip()
    .str.lower()
    .str.replace(" ", "_")
)
```

### 11.2 Convert Data Types

```python
sales["order_date"] = pd.to_datetime(
    sales["order_date"],
    errors="coerce",
)

sales["quantity"] = pd.to_numeric(
    sales["quantity"],
    errors="coerce",
)

sales["unit_price"] = pd.to_numeric(
    sales["unit_price"],
    errors="coerce",
)
```

### 11.3 Remove Duplicate Rows

```python
sales = sales.drop_duplicates()
```

### 11.4 Handle Missing Values

Example:

```python
sales = sales.dropna(
    subset=[
        "order_date",
        "product",
        "quantity",
        "unit_price",
    ]
)
```

Do not remove missing values automatically without considering their meaning.

Possible strategies include:

* Remove rows
* Fill with a constant
* Fill with the median
* Fill with the mode
* Forward fill
* Predict missing values
* Keep missing values as a separate category

### 11.5 Filter Invalid Records

```python
sales = sales[
    (sales["quantity"] > 0)
    & (sales["unit_price"] >= 0)
]
```

### 11.6 Create Derived Columns

```python
sales["revenue"] = (
    sales["quantity"] * sales["unit_price"]
)
```

Revenue can be written as:

```text
revenue = quantity x unit price
```

Example:

## 18. Step 7: Convert Repeated Code into Functions

Repeated logic should be extracted into functions.

Weak approach:

```python
sales["revenue"] = sales["quantity"] * sales["unit_price"]
```

The same calculation may be copied into several cells.

Better approach:

```python
def add_revenue_column(
    df: pd.DataFrame,
) -> pd.DataFrame:
    """Return a copy with a calculated revenue column."""

    result = df.copy()

    result["revenue"] = (
        result["quantity"]
        * result["unit_price"]
    )

    return result
```

Use the function:

```python
sales = add_revenue_column(sales)
```

Benefits:

* Easier to test
* Easier to reuse
* Easier to debug
* Less duplicated code
* Simpler conversion to scripts

## 19. Use Functions for Data Validation

Example:

```python
def validate_sales_data(
    df: pd.DataFrame,
) -> None:
    """Raise errors when important data rules are violated."""

    required_columns = {
        "order_id",
        "order_date",
        "product",
        "quantity",
        "unit_price",
    }

    missing_columns = (
        required_columns - set(df.columns)
    )

    if missing_columns:
        raise ValueError(
            f"Missing columns: {sorted(missing_columns)}"
        )

    if df["order_id"].isna().any():
        raise ValueError(
            "order_id contains missing values"
        )

    if (df["quantity"] <= 0).any():
        raise ValueError(
            "quantity must be greater than zero"
        )

    if (df["unit_price"] < 0).any():
        raise ValueError(
            "unit_price cannot be negative"
        )
```

Run the validation:

```python
validate_sales_data(sales)
```

Validation converts assumptions into executable rules.

## 20. Avoid Hidden State

A notebook has **hidden state** when its result depends on cells that were executed earlier but are no longer visible in the logical workflow.

Example:

```python
discount_rate = 0.10
```

Later:

```python
sales["discounted_revenue"] = (
    sales["revenue"] * (1 - discount_rate)
)
```

If the first cell is not executed, the second cell fails.

A more dangerous case occurs when a variable contains an old value from a previous experiment.

To reduce hidden state:

* Define variables before use.
* Keep configuration near the top.
* Avoid redefining the same variable many times.
* Restart the kernel regularly.
* Run all cells from top to bottom.
* Avoid manual modifications outside the notebook.

## 21. Execution Order Problems

Notebook cells can be executed in any order.

For example:

```text
Cell 1: Load data
Cell 2: Clean data
Cell 3: Create revenue column
Cell 4: Draw chart
```

The correct order is:

```text
1 -> 2 -> 3 -> 4
```

But a user may execute:

```text
1 -> 3 -> 2 -> 4
```

This can produce incorrect results or errors.

Before sharing a notebook:

```text
Save the notebook
        |
        v
Restart the kernel
        |
        v
Clear old variables
        |
        v
Run all cells
        |
        v
Check for errors
        |
        v
Verify outputs
        |
        v
Save the final version
```

In Jupyter, use:

```text
Kernel -> Restart Kernel and Run All Cells
```

## 24. Distinguish Observation from Explanation

An **observation** describes what the data shows.

Example:

```text
Revenue decreased by 18% in April.
```

An **explanation** proposes why it happened.

Example:

```text
Revenue may have decreased because order volume fell.
```

Do not present an untested explanation as a confirmed fact.

Better writing:

```markdown
Revenue decreased by 18% in April. The decline coincides with a reduction in order volume, but additional evidence is required to establish causation.
```


## 27. Prevent Data Leakage

Data leakage occurs when information from the validation or test set influences model training.

Incorrect workflow:

```text
Full dataset
    |
    v
Calculate preprocessing statistics
    |
    v
Split into train and test
```

Correct workflow:

```text
Full dataset
    |
    v
Split into train and test
    |
    +----------------------+
    |                      |
    v                      v
Training data          Test data
    |                      |
    v                      |
Fit preprocessing          |
    |                      |
    +----------+-----------+
               |
               v
Apply learned preprocessing
```

For example, calculate a mean value using only the training data.

```python
train_mean = X_train["age"].mean()

X_train["age"] = (
    X_train["age"].fillna(train_mean)
)

X_test["age"] = (
    X_test["age"].fillna(train_mean)
)
```

Do not calculate a separate mean from the test set.

## 30. When Code Should Leave the Notebook

Move code into a script or module when:

* The same logic appears in several cells.
* The code is used by multiple notebooks.
* The transformation must run regularly.
* The function requires unit tests.
* The workflow will be deployed.
* The code is becoming difficult to navigate.
* The notebook takes a long time to execute.
* The logic is part of an API or data pipeline.

Keep the notebook focused on:

* Exploration
* Experimentation
* Explanation
* Visualization
* Interpretation

Move stable logic into:

* Python functions
* Python modules
* SQL files
* Configuration files
* Pipeline tasks
* APIs

* Clear irrelevant output.
* Remove API keys and passwords.
* Restart the kernel.

* Verify charts and tables.

* Write conclusions.
* Save the notebook.

## 34. Common Mistakes

### 34.1 Running Cells Out of Order

Problem:

The notebook depends on old variables from a previous execution.

Solution:

Restart the kernel and run all cells.

---

### 34.2 Modifying Raw Data Manually

Problem:

The original data cannot be recovered or compared.

Solution:

Keep raw data unchanged and create processed outputs separately.

```text
data/raw/
data/interim/
data/processed/
```

---

### 34.3 Mixing All Tasks in One Cell

Problem:

The cell is difficult to debug and reuse.

Solution:

Separate loading, cleaning, analysis, and visualization.

---

### 34.4 Repeating Code

Problem:

The same logic is copied across many cells.

Solution:

Create a reusable function.

---

### 34.5 Using Hard-Coded Paths

Weak:

```python
df = pd.read_csv(
    "C:/Users/name/Desktop/project/data.csv"

```

Better:

```python
DATA_PATH = Path("../data/raw/data.csv")
```

### 34.6 Showing Charts Without Insights

Problem:

The reader sees the visualization but does not know why it matters.

Solution:

Write an observation, interpretation, and recommendation.

### 34.7 Drawing Conclusions Without Evidence

Problem:

The notebook presents guesses as facts.

Separate observations from hypotheses.

## 35. Practical Demo Workflow

The following workflow can be used for a small sales dataset.

### Step 1: Load the Data

```python
from pathlib import Path

import matplotlib.pyplot as plt
import pandas as pd

DATA_PATH = Path("../data/raw/sales.csv")

sales_raw = pd.read_csv(DATA_PATH)
sales = sales_raw.copy()
```

### Step 2: Inspect the Dataset

```python
print("Shape:", sales.shape)

display(sales.head())
display(sales.dtypes)
display(sales.isna().sum())
```

### Step 3: Clean the Dataset

```python
sales.columns = (
    sales.columns
    .str.strip()
    .str.lower()
    .str.replace(" ", "_")
)

sales["order_date"] = pd.to_datetime(
    sales["order_date"],
    errors="coerce",
)

sales["quantity"] = pd.to_numeric(
    sales["quantity"],
    errors="coerce",
)

sales["unit_price"] = pd.to_numeric(
    sales["unit_price"],
    errors="coerce",
)

sales = sales.drop_duplicates()

sales = sales.dropna(
    subset=[
        "order_date",
        "quantity",
        "unit_price",
    ]
)

sales = sales[
    (sales["quantity"] > 0)
    & (sales["unit_price"] >= 0)
]

sales["revenue"] = (
    sales["quantity"] * sales["unit_price"]
)
```

### Step 4: Create an Analysis Table

```python
product_summary = (
    sales.groupby(
        "product",
        as_index=False,
    )
    .agg(
        units_sold=("quantity", "sum"),
        total_revenue=("revenue", "sum"),
    )
    .sort_values(
        "total_revenue",
        ascending=False,
    )
)

product_summary.head(10)
```

### Step 5: Create a Chart

```python
top_products = product_summary.head(10)

top_products.plot(
    x="product",
    y="total_revenue",
    kind="bar",
    legend=False,
    title="Top 10 Products by Revenue",
)

plt.xlabel("Product")
plt.ylabel("Total Revenue")
plt.xticks(rotation=45)
plt.tight_layout()
plt.show()
```

### Step 6: Write an Insight

```markdown
### Insight 1: Revenue Concentration

The top three products contribute a large share of total revenue. This creates concentration risk because a decline in demand for one of these products could have a significant effect on overall sales.
```

### Step 7: Save the Result

```python
OUTPUT_PATH = Path(
    "../reports/product_summary.csv"
)

OUTPUT_PATH.parent.mkdir(
    parents=True,
    exist_ok=True,
)

product_summary.to_csv(
    OUTPUT_PATH,
    index=False,
)
```

## 38. Insight Writing Template

Use this structure for each important result:

```markdown
### Insight

**Observation:** What does the table or chart show?

**Possible explanation:** What factors may explain the pattern?

**Business or research implication:** Why does the pattern matter?

**Recommendation:** What action or further analysis should be performed?

**Caveat:** What limitation affects this conclusion?
```

Example:

```markdown
### Insight: Regional Sales Decline

**Observation:** Revenue in the Central region decreased by 22% during the final two months.

**Possible explanation:** The decline coincides with a reduction in order volume rather than lower average prices.

**Implication:** The problem may relate to customer demand or distribution coverage.

**Recommendation:** Compare customer retention and inventory availability across regions.

**Caveat:** The dataset does not contain marketing campaign or stockout information.
```

## 42. Summary

A **Notebook Workflow** is a structured and reproducible process for performing data analysis or model experimentation inside an interactive notebook.

A strong notebook should include:

* A clear problem statement
* Organized imports and configuration
* Reproducible data loading
* Data validation
* Explicit cleaning steps
* Focused analysis cells
* Meaningful charts and tables
* Written interpretations
* Assumptions and limitations
* Programmatically saved outputs
* A clear path from exploration to reusable code

The recommended workflow is:

```text
Define
    ->
Load
    ->
Validate
    ->
Clean
    ->
Explore
    ->
Transform
    ->
Analyze or model
    ->
Evaluate
    ->
Interpret
    ->
Save
    ->
Refactor
    ->
Version with Git
```

A notebook should not be treated as a temporary collection of code cells. It should be a reproducible analysis document that another person can execute, understand, verify, and extend.
