## 1. Lesson Overview

**Maximum Tokens** is a request parameter that places an upper limit on how many tokens a language model may generate for a response.

It helps an AI engineer control:

* Response length
* Token usage
* API cost
* Worst-case generation time
* User-interface limits
* Structured-output reliability
* Resource allocation
* Long-running generation tasks

In the current OpenAI Responses API, this parameter is named:

```text
max_output_tokens
```

It represents an upper bound on generated tokens. For models that use internal reasoning tokens, the limit can include both visible output and reasoning tokens.

The parameter does **not** guarantee that the model will generate exactly that number of tokens. A model may stop earlier when it:

* Completes the task
* Produces a natural stopping point
* Encounters a stop condition
* Calls a tool
* Reaches a safety restriction
* Reaches the configured token limit

## 3. What Is a Token?

A token is a unit of text processed by a language model.

A token may be:

* A complete word
* Part of a word
* Punctuation
* Whitespace
* A number
* A symbol
* Part of a code expression

For example, this sentence:

```text
AI engineering is exciting.
```

might be divided conceptually into units such as:

```text
AI | engineering | is | exciting | .
```

However, tokenization does not always match words exactly.

A longer or less common word may be split into several tokens:

```text
internationalization
```

Conceptually:

```text
international | ization
```

Code, numbers, multilingual text, and unusual formatting may also produce different token counts.

Therefore:

```text
1 token ≠ always 1 word
```

Do not estimate production usage only by counting words or characters.

## 4. Input Tokens and Output Tokens

A model request generally contains two major token categories.

### Input tokens

Input tokens include content sent to the model, such as:

* Developer instructions
* System instructions
* User messages
* Previous conversation messages
* Retrieved RAG passages
* Tool definitions
* Images or audio represented by model-specific token accounting
* Examples included in the prompt

### Output tokens

Output tokens are generated by the model, including:

* Visible response text
* Structured JSON
* Tool calls and their arguments
* Reasoning tokens for models that use internal reasoning
* Other generated output supported by the endpoint

The Responses API usage object reports `input_tokens`, `output_tokens`, token details, and `total_tokens`.

```text
Total token usage
      =
Input tokens
      +
Output tokens
```

A request can therefore use many tokens even when the final visible answer is short.

## 6. What `max_output_tokens` Means

Consider this request:

```javascript
max_output_tokens: 300
```

This means:

> The model may generate up to 300 output tokens for this response.

It does not mean:

> The model must generate exactly 300 tokens.

The output could use:

```text
42 tokens
128 tokens
247 tokens
300 tokens
```

The actual number depends on the prompt, model behavior, tools, output format, and stopping conditions.

The lesson source also demonstrates that setting a small output limit can cut the answer off, while a larger limit permits a more complete response. It emphasizes that the parameter controls model output rather than the size of the input prompt.

## 7. Upper Bound vs. Target Length

Maximum tokens is a **hard budget**, not a precise writing-length instruction.

Compare these two controls:

### API limit

```javascript
max_output_tokens: 500
```

This controls the maximum number of generated tokens.

### Prompt instruction

```text
Answer in approximately 150 words.
```

This communicates the desired response length.

For better control, use both:

```javascript
const response = await client.responses.create({
  model: process.env.OPENAI_MODEL,
  input: "Explain vector databases in approximately 150 words.",
  max_output_tokens: 300,
});
```

The prompt provides a target. The API parameter provides a safety boundary.

```text
Prompt length instruction
        ↓
Desired response size

max_output_tokens
        ↓
Maximum allowed generation
```

## 8. Context Window and Token Budget

Every model has a context-window limit.

The context window must accommodate the request context and the generated output.

A simplified relationship is:

[
\text{Input Tokens} + \text{Available Output Tokens}
\leq
\text{Context Window}
]

For example:

```text
Model context window: 32,000 tokens
Input context:        24,000 tokens
Potential output:      8,000 tokens
```

Conceptually:

```text
┌──────────────────── 32,000-token context ────────────────────┐
│                                                             │
│  Input: 24,000 tokens        Output capacity: 8,000 tokens  │
│  ████████████████████████    ████████                       │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

If the input grows, less space remains for output.

```text
Longer input
    ↓
Less remaining context capacity
    ↓
Smaller possible response
```

For the Responses API, truncation is disabled by default. When the input exceeds the model’s context capacity, the request can fail rather than silently removing content. The API also supports an automatic truncation strategy that may remove earlier conversation items to fit the request.

## 9. Maximum Tokens and Reasoning Models

For some reasoning models, the output-token budget can include:

```text
Internal reasoning tokens
          +
Visible answer tokens
```

Suppose the request uses:

```javascript
max_output_tokens: 1000
```

A conceptual allocation could be:

```text
Reasoning tokens: 700
Visible answer:   300
Total output:   1,000
```

Therefore, a limit of 1,000 does not always mean the user will receive 1,000 visible tokens.

The Responses API defines `max_output_tokens` as an upper bound that includes visible output tokens and reasoning tokens. Its usage details can separately report reasoning-token consumption.

This matters when using reasoning models for:

* Complex coding
* Mathematical analysis
* Planning
* Multi-step decisions
* Agent orchestration
* Difficult classification tasks

A very small output budget may leave insufficient room for either reasoning or the final answer.

## 10. Parameter Names Across APIs

The general concept is often called **maximum tokens**, but the exact parameter name depends on the API.

| API surface                            | Common parameter                                   |
| -------------------------------------- | -------------------------------------------------- |
| Responses API                          | `max_output_tokens`                                |
| Modern Chat Completions configurations | `max_completion_tokens`                            |
| Realtime API                           | `max_output_tokens` or session-specific equivalent |
| Older APIs or examples                 | `max_tokens`                                       |

For new applications, check the documentation for the exact endpoint and selected model rather than copying a parameter from an old tutorial.

This lesson primarily uses:

```text
Responses API → max_output_tokens
```

## 11. Basic JavaScript Example

Install the OpenAI SDK:

```bash
npm install openai
```

Set the API key as an environment variable. The official SDK can automatically read `OPENAI_API_KEY` from the environment.

```bash
export OPENAI_API_KEY="your_api_key_here"
export OPENAI_MODEL="your-supported-model"
```

Create `maximum-tokens-demo.mjs`:

```javascript
import OpenAI from "openai";

const client = new OpenAI();

const model = process.env.OPENAI_MODEL;

if (!model) {
  throw new Error(
    "OPENAI_MODEL is missing. Set it to a model available to your account.",
  );
}

async function generateExplanation() {
  const startedAt = performance.now();

  try {
    const response = await client.responses.create({
      model,
      input: [
        {
          role: "developer",
          content:
            "You are an AI engineering instructor. Explain concepts clearly.",
        },
        {
          role: "user",
          content:
            "Explain the difference between input tokens and output tokens.",
        },
      ],
      max_output_tokens: 300,
    });

    const latencyMs = Math.round(performance.now() - startedAt);

    console.log("Response:");
    console.log(response.output_text);

    console.log("\nMetrics:");
    console.log({
      status: response.status,
      latencyMs,
      inputTokens: response.usage?.input_tokens ?? null,
      outputTokens: response.usage?.output_tokens ?? null,
      reasoningTokens:
        response.usage?.output_tokens_details?.reasoning_tokens ?? null,
      totalTokens: response.usage?.total_tokens ?? null,
      incompleteReason: response.incomplete_details?.reason ?? null,
    });
  } catch (error) {
    if (error instanceof Error) {
      console.error("Model request failed:", error.message);
    } else {
      console.error("An unknown error occurred:", error);
    }

    process.exitCode = 1;
  }
}

await generateExplanation();
```

The response usage fields allow an application to record input, output, reasoning, and total token consumption.

## 12. Comparing Different Limits

A single API call does not show how maximum tokens affects a product.

Test several limits with the same prompt:

```javascript
import OpenAI from "openai";

const client = new OpenAI();

const model = process.env.OPENAI_MODEL;

if (!model) {
  throw new Error("OPENAI_MODEL is required.");
}

const outputLimits = [30, 100, 300, 800];

async function testLimit(maxOutputTokens) {
  const startedAt = performance.now();

  try {
    const response = await client.responses.create({
      model,
      input: `
Explain Retrieval-Augmented Generation.

Include:
1. The problem it solves
2. Its main components
3. A request-flow example
4. Two limitations
      `.trim(),
      max_output_tokens: maxOutputTokens,
    });

    return {
      maxOutputTokens,
      status: response.status,
      text: response.output_text,
      latencyMs: Math.round(performance.now() - startedAt),
      inputTokens: response.usage?.input_tokens ?? 0,
      outputTokens: response.usage?.output_tokens ?? 0,
      reasoningTokens:
        response.usage?.output_tokens_details?.reasoning_tokens ?? 0,
      totalTokens: response.usage?.total_tokens ?? 0,
      incompleteReason: response.incomplete_details?.reason ?? null,
    };
  } catch (error) {
    return {
      maxOutputTokens,
      error: error instanceof Error ? error.message : String(error),
    };
  }
}

const results = [];

for (const outputLimit of outputLimits) {
  results.push(await testLimit(outputLimit));
}

for (const result of results) {
  console.log("\n================================");
  console.log(`Maximum output tokens: ${result.maxOutputTokens}`);
  console.log(`Status: ${result.status ?? "error"}`);
  console.log(`Output tokens: ${result.outputTokens ?? "unknown"}`);
  console.log(`Latency: ${result.latencyMs ?? "unknown"} ms`);
  console.log(`Incomplete reason: ${result.incompleteReason ?? "none"}`);
  console.log("--------------------------------");
  console.log(result.text ?? result.error);
}
```

Expected observations:

| Limit | Likely behavior                           |
| ----: | ----------------------------------------- |
|  `30` | Very short or incomplete                  |
| `100` | Brief explanation                         |
| `300` | Moderate detail                           |
| `800` | More room, but not necessarily fully used |

## 13. Detecting an Incomplete Response

A response may stop because the configured output budget was reached.

Conceptually:

```text
Model begins generating
        ↓
Output budget is consumed
        ↓
Generation stops
        ↓
Response status becomes incomplete
```

The Responses API can return an incomplete status with details indicating that the output-token limit was reached.

Example check:

```javascript
function reachedTokenLimit(response) {
  if (response.status !== "incomplete") {
    return false;
  }

  const reason = response.incomplete_details?.reason;

  return reason === "max_output_tokens" || reason === "max_tokens";
}
```

Use it after the request:

```javascript
if (reachedTokenLimit(response)) {
  console.warn(
    "The response may be incomplete because it reached the output-token limit.",
  );
}
```

Do not return truncated content to the user as though it were complete.

## 14. Why Responses Get Cut Off

A limit that is too low may produce:

* An unfinished sentence
* Invalid JSON
* Missing list items
* A story ending in the middle of a scene
* Incomplete source code
* An unfinished Markdown code block
* Missing citations
* Partial tool arguments
* A summary that omits important sections

Example:

```text
The main components of a RAG system are the document loader,
chunking pipeline, embedding model, vector database, retriever,
and the generation model. During a request, the application first
```

The output stops before completing the explanation.

A small output limit is especially risky for:

* Structured JSON
* Long-form reports
* Multi-file code generation
* Stories
* Detailed reasoning
* RAG answers with citations
* Tool calls with complex arguments

## 15. Maximum Tokens and Structured Output

Suppose the expected response is:

```json
{
  "summary": "A short summary",
  "sentiment": "positive",
  "topics": ["AI", "education"],
  "confidence": 0.91
}
```

If the token limit is too low, the model could return:

```json
{
  "summary": "A short summary",
  "sentiment": "positive",
  "topics": [
```

This is invalid JSON.

```text
Low output limit
      ↓
Truncated structure
      ↓
Parsing failure
      ↓
Application error
```

A production workflow should use:

```text
Sufficient output budget
        +
Structured Output schema
        +
Parser
        +
Business-rule validation
        +
Retry or repair policy
```

Maximum tokens should provide enough room for the largest valid response allowed by the schema.

## 16. Maximum Tokens and Cost

API cost is generally calculated from actual token usage, not simply from the configured maximum.

A simplified formula is:

[
\text{Input Cost}
=================

\frac{\text{Input Tokens}}{1{,}000{,}000}
\times
\text{Input Price per Million}
]

[
\text{Output Cost}
==================

\frac{\text{Output Tokens}}{1{,}000{,}000}
\times
\text{Output Price per Million}
]

[
\text{Total Cost}
=================

\text{Input Cost}+\text{Output Cost}
]

Example utility:

```javascript
function estimateCost({
  inputTokens,
  outputTokens,
  inputPricePerMillion,
  outputPricePerMillion,
}) {
  const inputCost =
    (inputTokens / 1_000_000) * inputPricePerMillion;

  const outputCost =
    (outputTokens / 1_000_000) * outputPricePerMillion;

  return {
    inputCost,
    outputCost,
    totalCost: inputCost + outputCost,
  };
}
```

Do not hard-code model prices permanently. Store current pricing in configuration because prices and model availability can change.

## 17. Maximum Tokens and Latency

Longer generated responses generally require more generation steps.

Conceptually:

```text
More output tokens
       ↓
More token-generation steps
       ↓
Potentially longer total response time
```

However:

```text
max_output_tokens: 2000
```

does not mean the model will always generate 2,000 tokens.

If the model completes the task in 150 tokens, it can stop naturally.

Maximum tokens mainly controls the **worst permitted output size**, while actual latency depends on:

* Actual generated token count
* Model choice
* Reasoning effort
* Provider load
* Network latency
* Tool calls
* Input length
* Streaming
* Retry behavior

---

## 18. Streaming Does Not Remove the Limit

Streaming sends output incrementally:

```text
Request
   ↓
Token chunk 1
   ↓
Token chunk 2
   ↓
Token chunk 3
   ↓
Completion
```

It improves perceived responsiveness because the user can begin reading before the full response is complete.

However:

```text
Streaming ≠ unlimited output
```

The maximum-output-token configuration still applies.

A streamed response can still:

* Reach the output limit
* Stop before completing a structure
* Fail during generation
* Be interrupted by a network error
* Require final status validation

The client should not assume that receiving several text chunks means the response completed successfully.

## 19. Selecting an Output Limit

The correct limit depends on the feature.

| Feature                      | Example starting budget |
| ---------------------------- | ----------------------: |
| Intent classification        |                  20–100 |
| Short entity extraction      |                  50–200 |
| Short customer-support reply |                 150–400 |
| Paragraph rewrite            |                 200–600 |
| Article summary              |               300–1,000 |
| Detailed explanation         |               500–1,500 |
| Structured report            |             1,000–4,000 |
| Story chapter                |             2,000–6,000 |
| Complex code generation      |          Task-dependent |

These are initial engineering hypotheses, not universal rules.

The final value should be selected using:

* Real prompts
* Representative input sizes
* Output validation
* Quality scoring
* Latency measurements
* Cost measurements
* Failure-rate analysis

Also verify the selected model’s supported output and context limits.

## 20. Feature-Specific Configuration

Avoid using one global output limit for every request.

```javascript
const generationProfiles = {
  classifyIntent: {
    maxOutputTokens: 60,
  },

  extractCustomerIssue: {
    maxOutputTokens: 250,
  },

  summarizeArticle: {
    maxOutputTokens: 700,
  },

  rewriteProfessionally: {
    maxOutputTokens: 600,
  },

  explainConcept: {
    maxOutputTokens: 1200,
  },

  generateStoryChapter: {
    maxOutputTokens: 4000,
  },
};
```

Request flow:

```text
User selects feature
        ↓
Application loads feature profile
        ↓
Prompt + model + output limit
        ↓
Model request
        ↓
Feature-specific validation
```

This makes cost and behavior easier to manage.

## 21. Input Length Should Affect the Budget

A static limit may not work for every input.

For example, a summarizer might calculate a budget based on the input size:

```javascript
function selectSummaryBudget(inputTokenEstimate) {
  if (inputTokenEstimate < 500) {
    return 200;
  }

  if (inputTokenEstimate < 2_000) {
    return 500;
  }

  if (inputTokenEstimate < 8_000) {
    return 1_000;
  }

  return 1_500;
}
```

However, the budget must also respect:

* Model output limits
* Remaining context capacity
* Product requirements
* User plan limits
* Cost policies

Conceptually:

```text
Requested output budget
        ↓
Compare with feature maximum
        ↓
Compare with model maximum
        ↓
Compare with remaining context
        ↓
Use the smallest safe value
```

## 22. Output Length and Prompt Design

Increasing the maximum token limit does not guarantee a more complete answer when the prompt is unclear.

Weak prompt:

```text
Tell me about AI.
```

Better prompt:

```text
Explain artificial intelligence in four sections:

1. Definition
2. Main approaches
3. Real-world applications
4. Key limitations

Use 500–700 words and include one simple example.
```

Then provide enough capacity:

```javascript
max_output_tokens: 1200
```

Good output control combines:

```text
Clear structure
+ explicit target length
+ sufficient token budget
+ validation
```

## 23. Long-Form Generation Strategy

Generating an entire long document in one request can create:

* High latency
* High retry cost
* Inconsistent structure
* Truncation risk
* Lost work after a failure
* Weak continuity near the end
* Difficult validation

A better workflow divides the content into stages.

```text
User requirements
       ↓
Generate document plan
       ↓
Validate plan
       ↓
Generate Section 1
       ↓
Generate Section 2 using plan + Section 1 summary
       ↓
Generate Section 3
       ↓
Run consistency review
       ↓
Assemble final document
```

For a five-chapter story:

```text
Profile + wish
      ↓
Story plan
      ↓
Chapter 1
      ↓
Chapter-state summary
      ↓
Chapter 2
      ↓
Chapter-state summary
      ↓
...
      ↓
Final continuity review
```

Each stage receives its own output budget.

## 24. Continuation After Truncation

Automatically sending:

```text
Continue.
```

is often unreliable.

The model may:

* Repeat the previous paragraph
* Skip missing content
* Change formatting
* Produce duplicate JSON fields
* Lose the original structure

A better continuation request includes state:

```text
The previous response stopped after Section 2.

Continue with:
- Section 3: Limitations
- Section 4: Production checklist

Do not repeat Sections 1 or 2.
Start with the heading "## 3. Limitations".
```

For code, include:

* The last complete function
* The required remaining functions
* Expected imports
* Output format
* A clear continuation boundary

For structured data, it is usually safer to regenerate the full object with a larger budget than to concatenate partial JSON.

## 25. Retry Policy

Not every incomplete response should be retried automatically.

A reasonable strategy is:

```text
Request
   ↓
Was it incomplete because of token limit?
   ├── No → process normally
   │
   └── Yes
        ↓
Is the task safe to continue?
   ├── No → return a controlled error
   │
   └── Yes
        ↓
Increase budget or split the task
        ↓
Retry once
        ↓
Validate final result
```

Example:

```javascript
async function generateWithSingleRetry({
  client,
  model,
  input,
  initialLimit,
  retryLimit,
}) {
  const firstResponse = await client.responses.create({
    model,
    input,
    max_output_tokens: initialLimit,
  });

  const firstReason = firstResponse.incomplete_details?.reason;

  const reachedLimit =
    firstResponse.status === "incomplete" &&
    (firstReason === "max_output_tokens" ||
      firstReason === "max_tokens");

  if (!reachedLimit) {
    return {
      response: firstResponse,
      retried: false,
    };
  }

  const retryResponse = await client.responses.create({
    model,
    input,
    max_output_tokens: retryLimit,
  });

  return {
    response: retryResponse,
    retried: true,
  };
}
```

Always cap retry counts to prevent:

* Infinite loops
* Duplicate charges
* Excessive latency
* Rate-limit pressure

## 26. Maximum Tokens in RAG

A RAG request contains several token consumers:

```text
Developer instructions
        +
User question
        +
Conversation history
        +
Retrieved passages
        +
Citation instructions
        +
Generated answer
```

Example budget:

```text
Model context capacity
        │
        ├── Instructions:        500 tokens
        ├── Conversation:      2,000 tokens
        ├── Retrieved context: 8,000 tokens
        ├── User question:       100 tokens
        └── Output reserve:    1,500 tokens
```

A common mistake is filling nearly the entire context window with retrieved documents and leaving insufficient room for the answer.

Better approach:

```text
Retrieve documents
       ↓
Rerank passages
       ↓
Remove irrelevant chunks
       ↓
Reserve output capacity
       ↓
Build final prompt
```

Maximum tokens cannot fix poor retrieval. It only limits the generation stage.

## 27. Maximum Tokens in Agent Systems

An agent may need output tokens for both text and tool calls.

```text
User request
    ↓
Model selects tool
    ↓
Model generates tool arguments
    ↓
Tool executes
    ↓
Model interprets tool output
    ↓
Model writes final answer
```

An output budget that is too low may cut off:

* Tool names
* JSON arguments
* SQL queries
* File paths
* Final explanations

Different agent stages should use different budgets.

| Agent stage            | Typical requirement |
| ---------------------- | ------------------- |
| Intent routing         | Small               |
| Tool selection         | Small               |
| Tool arguments         | Small to moderate   |
| Research synthesis     | Moderate to large   |
| Long report generation | Large               |
| Final confirmation     | Small               |

Tool schemas and application validation remain more important than simply increasing the token limit.

## 28. Maximum Tokens in an AI Writing Assistant

Project 3 contains several operations:

```text
Summarize
Rewrite
Translate
Explain
Return JSON
```

Each operation has a different output-length relationship.

### Summarize

The output should normally be shorter than the input.

```javascript
max_output_tokens: 500
```

### Rewrite

The output may be approximately the same length as the input.

```javascript
max_output_tokens: estimatedInputTokens * 1.5
```

### Translate

The translated text may be shorter or longer depending on the languages.

```javascript
max_output_tokens: estimatedInputTokens * 1.8
```

### Explain

The output may be much longer than the original question.

```javascript
max_output_tokens: 1200
```

### Structured JSON

The limit should be based on the maximum valid schema size.

```javascript
max_output_tokens: 400
```

Apply lower and upper boundaries:

```javascript
function clamp(value, minimum, maximum) {
  return Math.min(Math.max(value, minimum), maximum);
}

function calculateRewriteBudget(inputTokenEstimate) {
  return clamp(
    Math.ceil(inputTokenEstimate * 1.5),
    200,
    2_000,
  );
}
```

|   600 |           268 | Yes       |               4/4 | 1,310 ms |   4.6/5 |
| 1,200 |           271 | Yes       |               4/4 | 1,320 ms |   4.6/5 |

Possible conclusion:

```text
A limit of 300 tokens is sufficient for this prompt.

Higher limits do not materially improve quality because the model
naturally completes the answer at approximately 250–270 tokens.
```

## 30. Validation Checklist

After receiving a response, verify:

### Completion

* Did the response complete normally?
* Did it reach the token limit?
* Does it end with an unfinished sentence?
* Is a Markdown code block still open?

### Structure

* Is the JSON valid?
* Are all required fields present?
* Are all required headings present?
* Are list items complete?

### Content

* Did the model answer every requested part?
* Did it omit an important conclusion?
* Did it repeat content to fill space?
* Did it introduce unsupported claims?

### Operations

* How many tokens were consumed?
* What was the latency?
* Was a retry required?
* Did a rate-limit or timeout error occur?

## 32. Common Mistakes

### Mistake 1: Treating tokens as words

```text
500 tokens ≠ exactly 500 words
```

Tokenization varies across languages, code, punctuation, and text structure.

---

### Mistake 2: Expecting the model to use the full limit

```javascript
max_output_tokens: 1000
```

is an upper bound, not a request for exactly 1,000 tokens.

---

### Mistake 3: Setting the limit too low

This can produce:

* Invalid JSON
* Broken code
* Missing sections
* Unfinished prose

---

### Mistake 4: Setting an unnecessarily large limit

A very large limit may allow:

* Overly verbose answers
* Higher cost
* Longer worst-case latency
* Repetition
* Poor user experience

Use prompts and output limits together.

---

### Mistake 5: Ignoring reasoning tokens

For reasoning models, internal reasoning may consume part of the configured output budget.

---

### Mistake 6: Filling the context window with input

A large prompt or excessive RAG context can leave insufficient capacity for the answer.

---

### Mistake 7: Returning incomplete output without checking status

Applications should inspect completion status and incomplete details before presenting the result.

---

### Mistake 8: Using the same limit for every feature

Classification and chapter generation have very different requirements.

---

### Mistake 9: Retrying indefinitely

Retries must be capped and logged.

---

### Mistake 10: Assuming a larger limit improves intelligence

Maximum tokens controls available output capacity. It does not improve:

* Knowledge
* Reasoning ability
* Retrieval quality
* Factual accuracy
* Prompt understanding

## 37. Key Takeaways

1. Maximum Tokens places an upper bound on generated output.
2. In the Responses API, the main parameter is `max_output_tokens`.
3. The configured limit is not a guaranteed output length.
4. Input tokens and output tokens both contribute to total token usage.
5. The input and output must fit within the model’s context capacity.
6. Reasoning tokens may use part of the output-token budget.
7. A limit that is too low can create incomplete text, code, or JSON.
8. A limit that is too high may permit unnecessary verbosity and cost.
9. Streaming improves delivery but does not remove the output limit.
10. Applications must check response status and validate the result.
11. Different product features should use different output budgets.
12. Production limits should be selected through evaluation rather than guesswork.

## 38. Final Summary

Maximum Tokens is a core request-design control for LLM applications.

```text
Maximum output tokens
        ↓
Controls the output ceiling
        ↓
Influences worst-case length, cost, and latency
        ↓
May cause truncation when set too low
```

A reliable application combines:

```text
Clear prompt
    +
Appropriate output-token budget
    +
Context management
    +
Completion-status checking
    +
Output validation
    +
Token and cost logging
    +
Controlled retries
```

The goal is not to configure the largest possible limit.

The goal is to provide enough capacity for a correct and complete response while maintaining acceptable cost, latency, reliability, and user experience.
